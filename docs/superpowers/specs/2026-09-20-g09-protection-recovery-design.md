# G09 保护、恢复、删除与诊断设计

## 目标与范围

G09 在 G08 已完成的本地课程、资料、成果和反馈账本上建立可验证的保护与恢复闭环：持续写入中的 SQLite 能生成一致备份，持有人可用强口令跨机迁移，敏感资料可安全升级分类和永久删除，诊断信息默认最小化，并以故障注入和攻击样例验证边界。

本阶段按既定工作计划交付四个有序工作包：

1. G09-T01：一致备份和跨机加密恢复，交付备份恢复结果。
2. G09-T02：敏感重分类及彻底删除路径，交付安全测试。
3. G09-T03：诊断最小化与故障注入，交付诊断样包。
4. G09-T04：注入、越权及文件资源攻击测试，交付威胁检查清单。

本阶段不重做 G00–G08，不引入外部常驻服务，不开放 HTTP/WebSocket 监听，不把 API 密钥放入任何备份，也不声称普通文件删除等同于 SSD 物理安全擦除。真实 API、真实学生数据隐私授权、教学专业复核、干净 Windows、真实 Office/WPS、签名和发布继续独立记录；缺少这些条件时标记 `BLOCKED_EXTERNAL`，不得由测试替身或静态检查替代。

## 不可变约束

- SQLite 使用在线备份接口取得 WAL 一致快照；禁止只复制主 `.db` 文件。
- 备份先写应用私有临时位置，完成数据库校验、文件哈希和清单校验后再以原子重命名发布；半成品永不进入可用备份列表。
- API 密钥和 `credential` 表内容永不进入同机或跨机备份。跨机备份不能携带原机 DPAPI 包装后冒充可迁移密钥。
- 跨机归档整体使用认证加密；口令错误、密文、nonce、AAD 或归档内容被篡改时，在写入工作数据前失败，不返回部分明文。
- 恢复先在旁路目录完成版本、空间、哈希、路径、资源限制和 SQLite 完整性检查；只有全部通过才登记切换。切换失败必须恢复旧数据。
- 恢复后的 API 连接保持未配置；用户必须在目标机器重新连接模型服务。
- 自动备份默认每日首次成功业务写入后最多一份，保留 7 个日备份和 4 个周备份。空间不足时给出可恢复说明，不为腾空间删除唯一已知可恢复副本。
- 学生敏感原件、提取正文和结构化段使用 AES-256-GCM 加密；不得进入明文 SQLite 列、FTS、模型缓存、日志或诊断包。磁盘名称和诊断信息仅使用内部 ID 或通用标题。
- 普通资料升级为敏感资料时，在一个可回滚事务中先写认证密文，再清除明文原件、提取物、段、FTS 和派生缓存，并使旧引用失效。失败时保留升级前的完整可用状态。
- 永久删除覆盖应用控制范围内的原件、提取物、索引、敏感密文、派生敏感摘要和缓存，只保留不含正文的墓碑。外部导出的备份无法由应用召回，界面必须如实说明。
- 删除、恢复和覆盖操作必须由主进程签发短期、单次、绑定对象的确认令牌；渲染层或模型输出不能制造有效令牌。
- 诊断使用字段白名单，保存前展示完整预览，默认不上传；不包含原密钥、教材全文、学生正文、原文件名、任意本地路径或完整模型输入输出。
- 所有归档入口执行固定路径白名单、规范化路径检查、符号链接拒绝、条目数/单项大小/总展开大小/压缩比上限和加密容器大小上限。
- 每个 G09 工作包独立小提交，并同步更新 `PROGRESS.md` 与 `HANDOFF.md`。冻结验收文件不改状态、不删项目。

## 方案选择

采用“应用内保护子系统 + SQLite 在线快照 + 版本化 ZIP 载荷 + 认证加密信封 + 启动期原子切换”。该方案复用当前 `better-sqlite3`、Node `crypto`、`jszip`、Electron `safeStorage` 和原生文件对话框，不增加外部二进制或常驻服务。

不采用只备份数据库的方案，因为成果文件位于应用数据目录，单独数据库无法恢复完整课程包。不采用直接复制 `.db`、`-wal`、`-shm` 的方案，因为并发写入下难以形成可证明的一致快照。不采用 7-Zip、age 或系统 PowerShell 加密，因为干净 Windows 安装不能依赖额外命令，且外部进程会扩大口令和路径暴露面。

## G09-T01：一致备份与跨机恢复

### 备份对象与清单

新增 `protection` 领域。`BackupManager` 只从应用内部固定根目录工作，不接受渲染层任意源路径。一个备份载荷至少包含：

- `manifest.json`：格式版本、应用版本、schema 版本、备份 ID、创建时间、类型、文件条目、SHA-256、字节数和来源清单摘要；
- `data/yuwendesk.db`：由 SQLite Online Backup API 生成并经净化的快照；
- `materials/<内部 bundle id>/...`：数据库快照中已登记且哈希匹配的成果文件；
- 跨机包中的 `keys/workspace-key.json`：仅包含以备份密钥认证封装后的工作区数据密钥和算法参数，不包含 DPAPI blob 或 API 密钥。

数据库快照生成后以独立只读连接执行 `integrity_check`。随后删除快照中的 `credential` 行；同机备份保留当前机器可用的 `secure_key` 包装，跨机载荷移除 `secure_key` 行并把解封后的工作区数据密钥放入归档内部的二次 AES-GCM 包装。清单从已完成的数据库快照读取成果登记，再复制并重算文件哈希；数据库记录存在而文件缺失或不匹配时，备份失败而不是发布残缺包。

同机备份目录位于应用数据根的固定 `backups` 子目录。写入 `<backup-id>.partial`，校验后原子改名为 `<backup-id>.ready`。列表只读取命名正确、清单完整、哈希和数据库自检通过的 `.ready` 项。每日备份按本地日历日去重；每个 ISO 周保留一个周标记，轮换为最近 7 个日点和 4 个周点。同一快照可同时带日/周保留标签，避免无意义复制。删除候选前确认至少仍有一个已校验可恢复点；低磁盘导致新备份失败时保留旧备份。

### 跨机加密信封

便携文件扩展名为 `.yuwenbackup`。明文 ZIP 载荷只存在于应用私有临时目录，并在成功或失败后清理。外层信封包含最小版本头、KDF 参数、随机 salt、随机 96 位 nonce、密文长度和认证标签。版本头作为 AES-GCM AAD，密文覆盖完整 ZIP 字节。

口令使用 Node 内置 `scrypt` 派生 256 位备份密钥。运行时在受限参数集合中校准至约 250ms，最低 `N=32768,r=8,p=1`，最高 `N=131072`，内存上限明确；实际参数随信封保存。界面要求至少 14 个 Unicode 字符、拒绝空白和内置常见口令，但不承诺找回口令，也不设置后门。测试通过注入固定 KDF 参数保持可重复，不降低生产下限。

输出路径只由主进程原生保存对话框产生。渲染层提交口令和操作意图，不提交任意写入路径；口令只在一次调用内存中使用，不进入状态、日志、诊断或幂等记录。

### 旁路恢复与受控切换

恢复输入路径由主进程原生打开对话框产生。恢复器依次执行：

1. 检查容器大小、信封版本、KDF 参数上限和磁盘可用空间；
2. 认证解密完整容器；认证失败不向恢复目录写任何载荷；
3. 用固定允许路径解析 ZIP，拒绝绝对路径、`..`、反斜杠混淆、盘符、UNC、NUL、重复条目、符号链接及资源超限；
4. 在 `restore-staging/<job-id>` 校验清单、每项 SHA-256、schema 兼容性和 SQLite `integrity_check`；
5. 使用目标机器 `safeStorage` 重新包装工作区数据密钥，确保 `credential` 为空；
6. 由主进程显示范围、备份时间、将被替换的数据和“API 需重新连接”，签发绑定 job 的单次确认令牌；
7. 写入仅包含内部 job ID 和摘要哈希的 `pending-restore.json`，提示受控重启。

应用启动且数据库尚未打开时处理 pending restore：先把当前数据库和材料目录原子移至 `restore-rollback/<job-id>`，再把旁路数据移入正式位置并打开自检。若移动或自检失败，关闭新库并把 rollback 恢复原位；只有新库成功加载后才完成切换。旧 rollback 至少保留到一次成功启动结束，不在失败路径删除。恢复操作不尝试热换仍被服务对象持有的数据库。

### IPC 与界面

实现现有目录操作 `backup.create`、`backup.restore` 和 `backups.list`，并为应用管理的备份删除实现 `backups.delete`。`backup.create` 的模式为 `local` 或 `portable`；portable 模式要求口令和原生保存选择。`backup.restore` 先验证并返回恢复预览，再由绑定摘要的确认调用登记 pending restore。所有写调用使用幂等键；同键异载荷拒绝。

设置与帮助页显示最近备份、类型、校验状态、大小和保留标签；提供“立即创建本机备份”“导出跨机加密备份”“从备份恢复”。界面明确区分“已验证可恢复点”和“未完成/损坏项”，显示忘记口令不可找回、API 密钥不会迁移，以及恢复需要重启。

每日备份由 IPC 服务在一次成功业务写入后通知 `BackupCoordinator`。协调器按日合并重复请求并串行运行，不阻塞同一事务，不因窗口位置保存频繁触发，也不把备份失败改写成业务写入失败；失败作为可见维护警告和诊断元数据保存。

## G09-T02：敏感重分类与彻底删除

### 敏感载荷

新增 `source_sensitive_payload`，以 `version_id` 为主键，保存 AES-256-GCM 密文、随机 nonce、AAD、算法版本和明文哈希。AAD 固定包含内部工作区标识、document ID、version ID 和载荷版本。明文载荷是严格版本化对象，包含原件字节、提取全文、结构化段及必要 MIME 元数据；不包含原文件路径。加密使用现有工作区 256 位数据密钥，每次写入新 nonce。

学生敏感导入和普通资料升级到 `student_sensitive` 使用同一提交原语。事务在内存中构造并加密载荷，写入密文后删除该 version 的 `source_fts`、`source_seg_fts`、`source_segment`、`source_text` 以及 `source_file.original_blob`，把标题替换为由内部 ID 派生的通用标题，并更新分类。事务提交前任一步骤失败都会回滚，不能留下“已标敏感但仍有明文”或“明文已删但密文未写”的中间态。

首版只允许无损地提升到 `student_sensitive`；从敏感降级为普通分类必须通过重新导出、重新导入和独立隐私确认，`sources.reclassify` 不做静默解密降级。敏感正文仅通过受限本地读取方法按需解密，不进入 FTS、模型上下文或诊断。

### 引用失效和派生清理

重分类或删除时建立受影响 version ID 集合，清除引用这些版本的模型作业结果和缓存，删除或脱敏相关审查/反馈派生内容，并把相应课时 revision 标记为需要来源复核。历史计划对象不被伪造成仍有有效引用；UI 显示“来源已改为敏感/已删除，需要复核”。模型已产生的完整输入输出不得因历史保留原则继续保存敏感派生正文。

永久删除先停用资料，随后要求主进程双确认：第一次显示本机删除层，第二次显示备份范围、建议先导出合规备份以及 SSD 物理擦除不在保证范围。令牌绑定 document ID、当前 revision、选定备份处理策略和两分钟有效期，使用后立即失效。

删除事务按依赖顺序清除 FTS、段、正文、原件、敏感密文、版本、缓存和资料记录，写 `source_tombstone`，只保留内部 document ID、删除时间、删除原因代码和备份范围摘要。应用管理的同机备份通过清单识别是否含该 document；用户可在同一确认流程中删除这些备份并创建新的删除后恢复点。无法召回的外部 `.yuwenbackup` 文件在结果中明确列为用户控制范围，不宣称已清除。

## G09-T03：最小诊断与故障注入

`DiagnosticsService` 从字段白名单构造不可变预览：应用/平台版本、构建模式、schema 版本、保护态、各类对象计数、最近维护任务状态、备份数量与校验状态、错误代码计数和安全配置布尔值。对象标题、文件名、正文、路径、密钥、密文、prompt、模型完整输入输出和自由文本错误消息都不进入预览。

`diagnostics.export` 使用两阶段请求：`preview` 返回规范化 JSON 和 SHA-256；`save` 必须携带同一预览哈希并由主进程原生保存对话框选择位置。若状态变化导致哈希不同，要求重新预览。诊断 ZIP 仅包含 `diagnostics.json` 和说明范围的 `README.txt`，默认不发起网络请求或自动上传。

备份、恢复、重分类、永久删除和诊断保存均定义测试专用故障钩子。生产构造器不注入钩子；测试在 SQLite 快照后、清单发布前、密钥重包装后、pending marker 前、敏感密文写入后、FTS 清理后、删除中途和诊断原子重命名前抛错，验证事务回滚、半成品隔离、旧备份保留和旧数据可启动。连续三次相同维护失败时停止自动重试，保留错误代码和下一步，不把异常栈展示给教师。

## G09-T04：威胁验证

建立机器可执行的攻击夹具和人工证据清单：

- 材料中的“读取密钥、发送文件、忽略规则”等文本只能作为资料内容；它不能创建工具权限、网络许可、确认令牌或任意 IPC 操作。
- 伪造 sender、子 frame、未知 IPC 操作、跨对象 ID、额外 payload 字段和自造确认令牌全部拒绝。
- 便携包的 `../`、绝对路径、盘符、UNC、Unicode/分隔符混淆、重复项、符号链接、超量条目、超大展开体积和异常压缩比在写入工作目录前拒绝。
- 密文、tag、nonce、AAD、KDF 参数和 manifest 任一被篡改均失败；错误口令不改变现库。
- DOCM/OOXML 关系、HTML/脚本、PDF 动作和外链图片在导入/预览中不执行；主窗口不导航到不可信页面。
- 当前版本没有 URL 下载资料能力，因此 IPC 必须拒绝 URL 作为本地导入路径。`SEC-006` 保留为未完成验收；未来启用下载前必须加入每次重定向重新解析 DNS/IP 并阻断 localhost、私网、链路本地和元数据地址的实际集成测试，不能以初始 URL 静态校验冒充通过。
- 生产构建无应用自建 HTTP/WebSocket 监听可由代码和进程检查形成工程证据；干净 Windows 标准账户上的真实监听/安装检查仍为 `BLOCKED_EXTERNAL`。

威胁报告逐项区分 `ENGINEERING_VERIFIED`、`NOT_RUN`、`NOT_APPLICABLE_CURRENT_CAPABILITY` 和 `BLOCKED_EXTERNAL`。冻结 acceptance JSON 保持不变，报告不能把单元测试自动提升为正式 P0/P1 验收通过。

## 错误处理与降级

- 在线快照或成果哈希失败：不发布新备份，旧备份保持可用。
- 空间不足：返回 `DISK_FULL`/备份空间不足说明，不轮换唯一恢复点。
- 口令太弱：在 KDF 前拒绝；口令错误或认证失败统一返回不可区分的恢复认证错误，不泄漏内部内容。
- 归档版本过新、schema 过新或清单缺失：拒绝恢复并保留现库。
- 归档资源或路径异常：删除旁路临时目录，记录内容无关错误码，不写正式目录。
- 目标机器 `safeStorage` 不可用：敏感数据备份不能登记恢复；现有数据不变。
- pending restore 切换失败：自动恢复 rollback；若 rollback 也失败则进入保护态并保留两套目录，不继续写入。
- 敏感升级失败：事务回滚，资料仍按原分类完整可用；不能只更新分类标签。
- 删除失败：原资料保持或回滚可见，不写成功墓碑；备份删除失败单独报告实际剩余项。
- 诊断状态在预览后变化：拒绝保存旧预览，要求重新确认；保存失败不留下可用半包。
- 外部环境缺失：只阻断相应真实验收，继续执行纯本地、无隐私数据、无需真实网络的任务。

## 测试与证据

所有生产行为按 TDD 实现，先运行能暴露缺失能力的失败测试，再写最小实现。每包运行定向测试、全量 Vitest、主/渲染 TypeScript、ESLint、`verify:contracts`、renderer/main build 和 `git diff --check`，记录实际命令、退出码、fixture 身份和阻断项。

### G09-T01

- WAL 持续写入时的在线快照包含调用前已提交事务，并通过独立恢复自检。
- 快照和 portable 包均无 `credential`；portable 恢复后 `secure_key` 由目标 `safeStorage` 新包装。
- 错误口令、篡改信封、篡改清单、过新 schema、空间不足和中断均不改变现库。
- `.partial` 不出现在可恢复列表；每日/每周轮换不删除唯一好副本。
- 成果文件缺失或哈希不符时备份失败，不发布“成功”。
- 恢复登记、启动切换、自检失败回滚和成功重启均有确定性测试。

### G09-T02

- 学生敏感导入和普通资料升级后，正文不存在于 `source_text`、segment、FTS、原件 blob、诊断和模型缓存。
